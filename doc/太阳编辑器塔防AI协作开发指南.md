# 太阳编辑器塔防地图 AI 协作开发指南

版本：1.0 · 日期：2026-10-13  
适用环境：Warcraft III 1.27、太阳编辑器、TypeScriptToLua、YD Lua、KK API、无内置 JAPI基线

## 一、文档目的

本文用于启动一张新的Warcraft III塔防地图，技术栈为：

```text
太阳编辑器（地图、物编、资源、编译和运行）
  → TypeScriptToLua（业务源码编译为Lua）
  → Warcraft III 1.27 + YD Lua（最终运行环境）
  → KK API（平台能力和轻量局间奖励存档）
  → AI辅助设计、编码、审查、测试编排和文档维护
```

本文提炼自《武道凌云》的实际开发经验，但不复制其ORPG架构。新项目是塔防地图：

- 一局内的塔、波次、敌人、金币、科技和战斗状态是主要状态；
- 局间只保存奖励、解锁、成就或货币等轻量数据；
- 不保存完整人物、装备背包、随机词缀或重型角色快照；
- 不应为了“以后可能需要”提前引入ORPG级存档协议。

文中“已验证”只表示在相同技术栈项目中经过源码和War3实机验证；具体KK后台额度、接口权限、限频和发布环境差异，仍须在新项目中重新验证。

## 二、先建立正确的技术认知

### 2.1 四层职责

| 层级 | 主要职责 | 不能替代什么 |
| --- | --- | --- |
| 太阳编辑器 | 地图编辑、物编、资源管理、TS编译、打包、启动、部分热更新 | 不能证明代码在War3运行时一定可用 |
| TypeScript/太阳框架 | 类型、模块、事件、计时、同步、Frame及常用工具 | 不是游戏规则，不保证所有声明接口都有运行时实现 |
| Warcraft III 1.27 + YD Lua | 单位、命令、路径、伤害、Frame和联机同步的最终执行环境 | 不能用编辑器预览代替实机验收 |
| KK API | 平台玩家、存档、房间和平台扩展能力 | 本地模拟不能证明真实服务器配额与失败行为 |

最重要的原则是：

> TypeScript编译通过只是第一关，Warcraft III实机运行才是最终裁判；本地KK模拟成功也不等于真实平台已经验收。

### 2.2 建议环境基线

新项目应先明确并写入README：

- Warcraft III版本；
- 太阳编辑器版本；
- Lua目标版本；
- 是否购买太阳内置JAPI；
- KK平台与本地模拟方式；
- 地图最大玩家数；
- Git仓库、地图解包目录和资源目录；
- 开发、测试、发布三种构建模式的差异。

如果没有购买内置JAPI，就以“无内置JAPI”作为硬约束，不允许业务模块暗中依赖只有声明、没有运行时实现的接口。

## 三、推荐工程结构

```text
map/game_root/
├─ src/
│  ├─ App.ts                    唯一入口与启动编排
│  ├─ StateConfigInit.ts        静态配置和框架开关
│  ├─ StateInit.ts              正式模块的确定性装配
│  ├─ AppCustom.d.ts            项目类型扩展
│  ├─ game/
│  │  ├─ config/                版本、稳定ID、波次和数值配置
│  │  ├─ core/                  生命周期、同步、日志和随机上下文
│  │  ├─ player/                玩家局内资源、离线和失败状态
│  │  ├─ build/                 建造、占地、升级、出售和退款
│  │  ├─ tower/                 塔定义、索敌、攻击和技能
│  │  ├─ enemy/                 敌人定义、路径、属性和回收
│  │  ├─ wave/                  波次状态机、生成计划和胜负条件
│  │  ├─ combat/                统一伤害与状态效果
│  │  ├─ reward/                局内结算与局间奖励
│  │  ├─ archive/               轻量存档版本、校验和KK适配
│  │  ├─ ui/                    建造、波次、结算和奖励界面
│  │  └─ test/                  地图内探针、固定预设和验收命令
│  └─ solar/                    太阳框架源码与声明，不放业务代码
├─ scripts/                     TS转Lua生成物，不手工修改
├─ lua/                         Lua运行库
├─ solar_asset/                 框架和项目公共资源
├─ xlsx/                        可选的配置数据源
├─ solar_boot.lua               Lua引导
└─ war3map.*                    地图、物编和触发器产物
```

工程规则：

- 业务代码只放在`src/game`等项目目录，不修改`src/solar`来实现业务需求；
- 不手工编辑TS生成的Lua脚本；
- `StateInit`只负责确定性装配，不堆放具体玩法实现；
- 配置、权威状态、表现和测试入口分开；
- 测试命令调用正式服务，不复制一套“测试专用玩法”。

## 四、新项目第一个工作日应该做什么

### 4.1 打通最小启动链

先完成以下链路：

```text
太阳编辑器编译
  → TypeScript转Lua
  → solar_boot.lua
  → App.ts
  → StateConfigInit
  → StateInit
  → War3画面显示版本标志
```

最低验收：

1. 编译无错误；
2. 地图能启动；
3. War3内显示明确版本号；
4. 太阳日志能找到对应TS函数堆栈；
5. 重新开局不会重复注册事件；
6. 单人和本地双开均可进入。

在这一步完成前，不要开发大量塔、敌人或UI。

### 4.2 建立可观察性

从第一天提供：

- 项目版本、配置版本和存档版本；
- 普通、战斗、同步、波次、存档五类日志开关；
- War3内短提示和本地文件详细日志；
- 安全的运行时错误探针；
- 当前波次、存活敌人数、已生成数和漏怪数的只读状态命令；
- 当前玩家金币、生命、塔数量和占地状态的只读命令。

不要通过关闭全局日志来解决刷屏。高频日志写文件，关键反馈才显示在War3画面。

### 4.3 建立Git基线

建议提交：

- TS源码；
- 地图和物编源文件；
- 正式使用的BLP、MDX、音效等资源；
- 设计文档、TODO和验收记录。

通常忽略：

- 编译生成的Lua脚本；
- `backup`、`cache`、`temp`；
- 本地日志和编辑器临时文件；
- 打包后的测试地图副本。

太阳编辑器可能在测试时改写`war3map.w3a/.w3t/.w3u`等对象文件。AI不得擅自回滚这些二进制修改；应先询问它们是否属于本次有效编辑器产物，再按功能分类提交。

## 五、同步、本地显示与联机安全

### 5.1 必须同步的塔防状态

以下操作必须在所有客户端以相同顺序执行：

- 创建、删除和移动敌人；
- 创建、升级、出售塔；
- 扣除和增加金币；
- 修改基地生命、漏怪数和胜负状态；
- 选择影响攻击结果的目标；
- 消耗战斗、掉落或奖励随机数；
- 启动、暂停、完成波次；
- 创建影响玩法的计时器、单位组、物品和特效；
- 写入局间奖励存档前的权威奖励计算。

### 5.2 只能本地执行的内容

`GetLocalPlayer()`分支适合：

- Frame显示与隐藏；
- 本地选中Tab、悬浮说明和提示文字；
- 镜头、音效和仅本机可见的表现；
- 不影响玩法的界面排序与筛选。

本地分支不得创建会进入同步状态的Unit、Group、Timer或随机结果。Frame按钮需要改变状态时，应发送“操作名＋最少参数”的同步请求，由同步处理器根据触发玩家重新验证。

建议采用统一网关：

```text
本地Frame点击
  → 同步短命令
  → 从同步事件取得triggerPlayer
  → 校验金币、位置、所有权、冷却和当前阶段
  → 调用正式服务提交
  → 各客户端刷新本地显示
```

永远不要相信载荷中的“玩家编号”。玩家身份必须取同步事件的触发玩家，防止客户端替其他玩家建塔、升级或领取奖励。

### 5.3 随机数

塔防常见随机包括：

- 塔的伤害浮动与暴击；
- 随机目标、连锁目标和分裂方向；
- 敌人词缀或特殊波次；
- 局末奖励抽取。

规则：

- 影响玩法的随机必须在同步逻辑中消耗；
- 同一次攻击的共享结果只随机一次，再复用于所有相关目标；
- 不依赖单位组的非稳定遍历顺序决定随机调用次数；
- 平台随机API存在网络和调用限制，不用于即时战斗；
- 调试模式支持固定种子或固定预设，便于复现。

## 六、塔防核心架构

### 6.1 波次必须是显式状态机

不要用多个互不知情的计时器拼接波次。建议状态：

```text
preparing   准备阶段
spawning    按计划生成
fighting    已生成完，等待清场
completed   波次完成并结算
failed      基地失败
finished    全部波次结束
```

每轮至少记录：

- `waveId`；
- 代次或令牌；
- 应生成总数；
- 已生成数；
- 当前存活数；
- 已击杀数；
- 已漏过数；
- 特殊敌人或首领状态；
- 开始、结束和结算时间；
- 当前难度和玩家人数快照。

所有延迟生成回调都携带波次令牌。波次取消、失败或重开后，旧回调发现令牌失效就直接退出，不能继续为新一局生成敌人。

### 6.2 计时器规范

- 简单一次性延迟使用`BaseUtil.runLater`；
- 固定循环任务优先使用`BaseUtil.onTimer`；
- 需要暂停、变速、长期持有或显式销毁时，才使用`STimer`或原生计时器；
- 不为每个敌人创建一个永久循环计时器；
- 同类行为尽量由集中更新器或事件驱动；
- 波次结束、玩家失败和重开时必须有统一清理入口。

### 6.3 敌人生成与回收

敌人服务应负责：

- 根据波次计划生成；
- 注册路径、阵营、属性、奖励和代次；
- 维护本轮敌人集合和存活计数；
- 死亡时注销伤害、防御、Buff、文本标签和奖励引用；
- 漏怪时只结算一次基地伤害；
- 卡位、走失和长期无进展时回位或回收；
- 波次取消与失败时清理残留单位；
- 防止旧代次敌人影响新一局。

不要每隔极短时间扫描全地图所有单位。优先持有正式生成的敌人集合，按有限范围和低频检查异常。

### 6.4 路径设计

路径是塔防项目的高风险区域，应尽早确定：

- 固定路径、动态迷宫还是混合模式；
- 玩家能否堵路；
- 空中单位是否绕过地面阻挡；
- 多出口、多基地和分叉如何选择；
- 闪现、击退、拉拽后如何恢复路径；
- 敌人到终点的判定是进入Rect、到达航点还是触发能力。

固定路径建议用明确航点序列和敌人当前航点索引。动态迷宫必须有建造前可达性校验；不能先扣钱建塔，再发现路径完全封死。

### 6.5 建造事务

一次正式建造应按事务处理：

1. 接收玩家建造意图；
2. 校验当前阶段允许建造；
3. 校验玩家、建造区域、占地、路径和金币；
4. 再次确认没有与其他同步建造冲突；
5. 扣除金币；
6. 创建塔并登记所有权和稳定实例ID；
7. 更新占地与UI；
8. 任一步失败不得留下半扣钱、半占地状态。

升级、出售和重建也应复用同一权威服务。出售退款由配置计算，不让UI自行推导。

### 6.6 塔的索敌与攻击

每类塔需要明确：

- 射程；
- 可攻击地面/空中类型；
- 目标优先级；
- 攻击间隔；
- 投射物与命中规则；
- 范围、连锁、穿透或持续伤害；
- Buff叠加、刷新和免疫规则。

建议优先级使用稳定、可解释的值，例如：

1. 距离终点最近；
2. 当前路径进度最高；
3. 首领或特殊标签；
4. 生命最低；
5. 稳定实例ID作为最终并列裁决。

不要只依赖War3单位组返回顺序，否则双开环境可能出现目标差异。需要可复现的目标列表时，先收集候选，再按稳定字段排序。

### 6.7 统一伤害入口

即使塔防的伤害系统比ARPG简单，也建议保留唯一提交入口：

```text
攻击/技能
  → 构建不可变攻击快照
  → 计算基础伤害、增益、抗性和暴击
  → 唯一DamageExecutor提交
  → 读取实际生命变化
  → 死亡、击杀奖励和清理
```

不要让不同塔散落调用`UnitDamageTarget`，否则难以统一击杀归属、护甲、免疫、统计和联机日志。太阳默认伤害规则是否启用，应由项目在最初的固定木桩测试中决定，不能边做塔边改变底层结算。

## 七、Frame UI兼容规范

### 7.1 已验证的硬边界

- `.d.ts`中有声明不代表War3 1.27运行时有实现；
- 无内置JAPI环境禁止使用`Frame.setLevel`和`FrameSetLevel`；
- 纯背景使用`BACKDROP`并调用`DzFrameSetIgnoreTrackEvents`；
- 不创建覆盖整个面板的透明`BUTTON`拦截点击；
- 按钮负责点击，背景和文字作为子Frame并忽略鼠标；
- 循环绑定Frame事件时，每轮创建稳定常量，避免TypeScriptToLua闭包都读到最终索引；
- 布局必须用War3截图验收，编辑器坐标和代码推算不能替代实机观察。

### 7.2 塔防UI建议

第一版只做：

- 当前波次、剩余敌人和基地生命；
- 玩家金币；
- 建造面板；
- 选中塔的等级、伤害、射程、攻速和升级/出售按钮；
- 下一波预告和准备按钮；
- 胜利、失败和局末奖励界面。

不要一开始制作复杂图鉴、排行榜或成长树。先保证从开局到结算不需要测试命令。

## 八、KK API与轻量局间奖励存档

### 8.1 新项目不需要ORPG快照

塔防项目只保存局间奖励时，建议持久化字段控制在少量稳定值：

- 存档协议版本；
- 累计局外货币；
- 已解锁塔或天赋的稳定ID集合；
- 成就位图或小型计数器；
- 最高通关难度/波次；
- 已领取的一次性奖励标记；
- 可选校验值。

不保存：

- 当前局塔实例；
- 单位handle；
- 当前波次和敌人状态；
- 临时Buff、投射物和计时器；
- 可以由配置和解锁状态重新推导的数据。

### 8.2 推荐存档策略

- 使用项目专属前缀Key，避免与其他地图或测试字段冲突；
- 存档格式有明确版本，升级时提供小型迁移函数；
- 一局奖励先在同步状态中计算，局末确认后再写入；
- 同一局奖励带局次令牌，防止重复点击或重复结算；
- 写入后立即回读并显示成功/失败，但不要因平台写入慢阻塞War3主流程；
- 只在结算、领取和少量关键节点写入，不按秒保存；
- 调试命令不能清空全部平台存档，只操作项目专属测试Key；
- 本地模拟和真实KK房间分别记录结论。

### 8.3 字符与额度

过往项目的保守经验是将单个Key/Value按最多63个ASCII字符设计。新项目应重新查证实际KK规则，但在真机验证前不要利用本地模拟器可能接受的更宽边界。

真实平台必须复验：

- Key和Value长度；
- 总额度与分项额度；
- 写入频率；
- 失败返回值；
- 跨局读取；
- 掉线和房主离开时的写入行为；
- 测试服与正式服是否共享数据。

## 九、AI与人的协作方式

### 9.1 人负责什么

人类开发者拥有最终产品和运行环境判断权，主要负责：

- 明确玩法目标、优先级和不可接受的设计；
- 在太阳编辑器中处理地形、物编、资源导入和可视化摆放；
- 编译地图并进入War3实测；
- 提供截图、报错堆栈、日志和明确复现步骤；
- 在真实KK房间完成平台和多人验证；
- 确认测试是否通过、是否勾选TODO、何时提交和发布。

### 9.2 AI负责什么

AI适合：

- 阅读仓库和现有规则后制定小步实现方案；
- 编写和重构TS业务代码；
- 建立测试命令、固定算例和状态审计；
- 检查同步边界、资源清理和失败路径；
- 编写精确的地图内测试步骤；
- 根据截图调整Frame布局；
- 维护TODO、实现记录、交接文档和提交说明；
- 在获得授权后分类提交和推送。

AI不能替代：

- War3实机的最终视觉和运行验证；
- 太阳编辑器中的地形与物编操作，除非存在可靠自动化入口；
- 真实KK服务器能力确认；
- 产品方向和数值手感的最终决策。

### 9.3 推荐的单项开发循环

```text
人：确认当前TODO和玩法边界
  ↓
AI：阅读相关源码与文档，说明本次实现范围
  ↓
AI：小范围实现＋静态检查＋测试步骤
  ↓
人：太阳编辑器编译＋War3实测
  ↓
人：反馈“通过”或提供截图/日志
  ↓
AI：修复或勾选TODO＋记录实测结论
  ↓
人授权后：AI分类提交、推送
  ↓
进入下一项
```

一次只实现一个可验收纵向切片。不要让AI连续完成十个功能后才第一次进地图测试。

### 9.4 给AI的信息应该包含什么

一个高质量任务至少说明：

- 当前目标；
- 明确不做的内容；
- 相关文件或系统；
- 玩家人数和测试环境；
- 预期交互；
- 是否允许修改地图、物编和资源；
- 是否需要提交、推送；
- 已知截图、报错和复现步骤。

示例：

```text
实现第一波正式流程：准备20秒后生成10只敌人，每1秒1只；
敌人沿现有三点路径前进，到终点扣1点基地生命并移除。
本项不做特殊敌人、奖励和下一波。
请复用WaveService和EnemyService，提供地图内测试步骤，先不要提交。
```

### 9.5 AI开始工作前必须做的检查

```text
git status --short
git log -10 --oneline --decorate
```

随后：

1. 阅读仓库根目录`AGENTS.md`；
2. 阅读最新HANDOFF和当前TODO；
3. 检查工作区是否有用户或编辑器未提交修改；
4. 搜索现有服务，避免重复实现；
5. 说明这一次的实现边界；
6. 修改后执行差异检查，不擅自提交。

### 9.6 AI不得做的事

- 未经确认回滚用户或编辑器修改；
- 使用`git reset --hard`等破坏性命令；
- 因为编译器声明存在就假定JAPI可用；
- 在本地UI分支修改同步状态；
- 直接用测试命令逻辑作为正式玩法；
- 为赶进度一次性勾选未经实测的TODO；
- 自动清空KK存档；
- 未经授权提交、推送或发布；
- 将临时测试代码长期留在正式服务中。

## 十、文档与验收体系

建议新项目从一开始维护：

```text
docs/
├─ 01-项目定位.md
├─ 02-核心玩法与单局流程.md
├─ 03-塔、敌人和波次规则.md
├─ 04-局间奖励与存档.md
├─ 05-联机与同步边界.md
├─ 06-MVP范围与决策.md
├─ 10-MVP阶段TODO.md
├─ 11-测试命令速查.md
├─ 12-工程与框架笔记.md
├─ 20-波次与敌人实现记录.md
└─ HANDOFF-日期.md
```

各文档职责：

- 设计文档：规则和产品决定；
- TODO：唯一执行状态；
- 实现记录：代码边界、测试步骤和实测证据；
- 测试命令速查：命令、参数、前置状态和清理方式；
- HANDOFF：当前Git状态、未提交修改、下一项起点和不可回退规则。

只有用户明确说“测试通过”后，才勾选对应TODO。编译通过、静态检查或AI自测都不能替代War3实测。

## 十一、塔防MVP推荐顺序

### M0：工程环境

- [ ] TS入口、日志、错误堆栈、重新开局；
- [ ] Frame最小面板；
- [ ] 本地双开和同步短命令；
- [ ] KK专属测试Key的读写与跨局验证。

### M1：最小可玩波次

- [ ] 固定路径和终点；
- [ ] 一种敌人；
- [ ] 波次状态机；
- [ ] 到终点扣基地生命；
- [ ] 死亡与漏怪都能正确减少存活计数；
- [ ] 波次清场后进入完成状态。

### M2：建造与一种塔

- [ ] 建造区域和占地校验；
- [ ] 金币事务；
- [ ] 一种塔的稳定索敌；
- [ ] 唯一伤害入口；
- [ ] 升级和出售；
- [ ] 建造UI。

### M3：完整单局

- [ ] 多波次配置；
- [ ] 准备、开始、清场和下一波；
- [ ] 普通、快速、耐久和首领敌人；
- [ ] 胜利、失败、重新开始；
- [ ] 局末奖励计算。

### M4：联机与难度

- [ ] 玩家加入、离线和共享/独立经济规则；
- [ ] 多玩家同时建造冲突；
- [ ] 人数和难度快照；
- [ ] 双开/四开波次、随机、击杀和结算一致；
- [ ] 房主离开与剩余玩家继续/失败规则。

### M5：局间奖励

- [ ] 轻量协议版本；
- [ ] 货币、解锁、成就和领取标记；
- [ ] 防重复结算；
- [ ] 本地模拟跨局；
- [ ] 真实KK房间额度和失败复验。

### M6：内容和表现

- [ ] 扩充塔、敌人、地图和难度；
- [ ] 音效、特效、图标和教程；
- [ ] 性能压力与长局测试；
- [ ] 数值曲线和平衡。

MVP完成条件不是“所有服务和测试命令存在”，而是玩家不输入测试命令即可完成：

```text
进入游戏 → 选择难度/准备 → 建塔 → 完成多波战斗
→ 胜利或失败 → 查看奖励 → 奖励可靠写入 → 下一局读取生效
```

## 十二、测试矩阵

### 12.1 每项至少覆盖

- 正常成功；
- 资源不足；
- 非法阶段；
- 重复点击；
- 上限与空状态；
- 玩家离线；
- 波次取消或失败；
- 重开后的旧回调；
- 单人和双人一致性；
- 清理后无残留。

### 12.2 波次专项

- 生成总数等于配置；
- 死亡数＋漏怪数＋存活数等于已生成数；
- 清场只结算一次；
- 旧代次敌人不影响新波次；
- 首领死亡与普通敌人死亡顺序不会重复完成；
- 玩家暂停、掉线或失败不会留下永久计时器。

### 12.3 建造专项

- 边界位置；
- 两名玩家同时点击同一格；
- 路径封堵；
- 金币刚好等于造价；
- 扣钱后创建失败的回滚；
- 升级上限；
- 出售退款和占地释放；
- 所有权校验。

### 12.4 性能专项

- 当前地图最大敌人数；
- 多塔同时索敌；
- 范围和连锁攻击；
- 大量TextTag、特效和投射物；
- 连续30分钟或完整最长难度；
- 波次间对象数量能回落；
- 日志开启与关闭时的差异。

## 十三、推荐的提交方式

按用途分类：

- `feat:` 正式玩法；
- `fix:` 缺陷修复；
- `test:` 测试命令和审计；
- `docs:` TODO、实现记录和交接；
- `asset:` PNG、BLP、MDX和音频；
- `chore:` 编辑器产物、配置或构建维护。

一次实测通过后，常见提交顺序：

1. 功能代码；
2. 地图/物编产物；
3. 素材；
4. 文档与TODO。

提交前至少执行差异检查，确认没有意外资源、临时文件和用户未授权的改动。推送前确认当前分支和远端。

## 十四、可直接复制的AGENTS.md基线

以下内容适合作为新项目起点，再按项目补充：

```markdown
# 工程约定

## 工作流

- 开始前阅读最新HANDOFF、当前TODO并执行git status。
- 保护用户和太阳编辑器产生的未提交修改，不使用破坏性Git命令。
- 每次只实现一个可验收切片；提供War3地图内测试步骤。
- 用户明确确认测试通过后，才勾选TODO和记录实测结论。
- 未经明确要求不提交、不推送、不发布。

## 延迟与计时器

- 简单一次性延迟使用BaseUtil.runLater。
- 循环任务优先使用BaseUtil.onTimer。
- 只有需要暂停、变速、长期持有或显式销毁时才使用STimer或原生计时器。
- 可刷新的延迟使用代次或令牌使旧回调失效。

## 同步

- Unit、Item、Group、Timer、金币、基地生命、波次、建塔、伤害和随机属于同步状态。
- GetLocalPlayer只用于Frame、镜头、音效和本地提示。
- Frame修改状态必须走同步网关；玩家身份取同步事件triggerPlayer。
- 不在本地分支创建玩法handle或消耗共享随机数。

## Frame兼容

- 目标环境为War3 1.27 + YD Lua；声明存在不等于运行时接口存在。
- 禁止Frame.setLevel和FrameSetLevel。
- 背景使用忽略鼠标事件的BACKDROP，不使用全面板透明BUTTON。
- 循环绑定回调时捕获每轮稳定常量。
- UI必须通过War3实机截图验收。

## 塔防状态

- 波次使用显式状态机和代次令牌。
- 正式敌人由统一服务登记，死亡、漏怪、取消和失败均须注销。
- 建造、升级和出售是事务；失败不得留下半扣钱或半占地。
- 索敌结果需要稳定裁决，不依赖单位组遍历顺序。
- 测试命令复用正式服务，不另写旁路玩法。

## KK存档

- 只保存局间货币、解锁、成就和领取标记等轻量状态。
- 使用项目专属Key和协议版本；不保存handle和当前局运行状态。
- 调试命令不得清空全部平台存档。
- 本地模拟结论与真实KK房间结论分开记录。
```

## 十五、常见风险速查

| 风险 | 处理 |
| --- | --- |
| TS编译通过但开图报空函数 | 检查无内置JAPI环境下接口是否真实存在 |
| Frame背景挡住按钮 | 背景使用BACKDROP并忽略鼠标，不叠全面板透明按钮 |
| 循环创建按钮全部触发最后一项 | 每轮捕获稳定常量 |
| 双开攻击不同目标 | 候选目标按路径进度和稳定ID排序 |
| 旧波次继续生成敌人 | 波次令牌使旧延迟回调失效 |
| 清场无法完成 | 统一登记死亡、漏怪、移除和存活计数 |
| 同一格被两人同时建造 | 同步处理器二次校验占地后再扣钱创建 |
| 本地UI点击导致不同步 | 只发送短命令，状态在同步处理器提交 |
| 奖励重复领取 | 局次令牌＋已领取标记＋幂等写入 |
| 本地KK正常、上线失败 | 真实房间重新验证额度、限频和返回值 |
| AI覆盖编辑器产物 | 开始前检查Git状态，二进制修改先向人确认 |
| 功能很多但不可玩 | 以零测试命令完整单局作为MVP完成条件 |

## 十六、最终建议

这套技术栈最稳妥的开发方式不是“让AI一次生成整张地图”，而是：

1. 人先锁定玩法和地图边界；
2. AI搭建可观察、可同步、可测试的最小服务；
3. 每个功能形成一个可在War3中独立验收的纵向切片；
4. 人负责编辑器和实机反馈，AI根据证据迭代；
5. 测试通过后再更新文档和提交；
6. 本地双开验证同步，真实KK房间验证平台；
7. 始终用“无需测试命令的完整单局”衡量是否真正可玩。

对于塔防项目，最值得优先做对的是波次状态机、敌人登记、建造事务、稳定索敌、同步边界和局末幂等奖励。塔的数量、特效丰富度和局外成长深度，都应建立在这些基础已经通过实机与多人验证之后。
